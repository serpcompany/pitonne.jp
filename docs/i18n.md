# Internationalization (i18n)

pitonne.jp supports English (default) and Japanese via a subdirectory URL structure.

## URL Structure

```
pitonne.jp/                      → English (default)
pitonne.jp/ja/                   → Japanese
pitonne.jp/services/iv-therapy/  → English service page
pitonne.jp/ja/services/iv-therapy/ → Japanese service page
```

English URLs have no `/en/` prefix. If someone visits `/en/...`, one 308 redirect strips it to `/...`.

## Architecture

- **Routing:** English pages are real bare routes under `src/app/(en)/`. Japanese pages are generated from `src/app/[locale]/` with `nonDefaultLocales`, currently only `ja`.
- **No Next.js middleware:** English is the default physical route structure. `/en/...` is handled by Cloudflare Pages redirects (`public/_redirects`), not by an internal rewrite.
- **No external i18n library.** Custom lightweight solution: locale config, JSON dictionaries, locale-aware data loading.

### Key Files

| File | Purpose |
|---|---|
| `src/lib/i18n/config.ts` | Locale types, constants (`locales`, `Locale`, `defaultLocale`) |
| `src/lib/i18n/dictionaries.ts` | Dictionary loader (`getDictionary(locale)`) |
| `src/lib/i18n/dictionaries/en.json` | English UI strings (nav, footer, buttons, headings) |
| `src/lib/i18n/dictionaries/ja.json` | Japanese UI strings |
| `src/app/(en)/` | Bare English route wrappers |
| `src/app/[locale]/` | Locale-aware page implementations and `/ja` routes |
| `public/_redirects` | Redirects `/en/*` to bare English paths |
| `src/lib/seo.ts` | `localizedCanonicalUrl()`, `localizedHreflangAlternates()`, `localizedPageMetadata()` |
| `src/lib/data/routes.ts` | `localizedRoute(path, locale)`, `getAreaNavigation(locale)` |

## Content

### Markdown Content (Services & Blog)

English and Japanese content are stored as sibling markdown files:

```
content/
  services/
    iv-therapy.md              ← English
    ja/
      iv-therapy.md            ← Japanese (same filename, ja/ subdirectory)
  blog/
    iv-therapy-for-fatigue.md  ← English
    ja/
      iv-therapy-for-fatigue.md ← Japanese
```

Slugs, canonical paths, category slugs, and all identifier fields stay in English across both versions. Only human-readable text (title, description, body, FAQs, benefits, etc.) is translated.

Services and legal pages pair strictly: each file in [`content/services/`](../content/services/) has a Japanese file
of the same name in [`content/services/ja/`](../content/services/ja/), and each file in
[`content/pages/legal/`](../content/pages/legal/) has one in [`content/pages/legal/ja/`](../content/pages/legal/ja/).
`src/lib/i18n/content-parity.test.ts` fails when either side is missing.

Blog posts are the exception to strict pairing: a post may be published in one locale only, and `draft: true` posts are never built. See [ADR 0001](adr/0001-blog-cms.md).

### Data Layer

All data functions accept an optional `locale` parameter defaulting to `'en'`:

```ts
getService("iv-therapy", "ja")       // Japanese service data
getAllBlogPosts("ja")                 // Japanese blog posts
getBlogPostBySlug("iv-therapy-for-fatigue", "ja")
getServiceCategorySections("ja")     // Returns Japanese category titles
getBusinessInfo("ja")                // Japanese business description + day names
```

### UI Strings

Header, Footer, and page chrome use JSON dictionaries:

```ts
const dict = getDictionary(locale)
dict.nav.services    // "サービス"
dict.footer.openHours // "営業時間"
dict.common.contactUs // "お問い合わせ"
```

A client component (`'use client'`, such as the Header) never imports the dictionaries, because React would ship
both of them in its JavaScript. The server picks the strings it renders and passes them as props (`getHeaderText`
in `src/components/header-text.ts`); `src/lib/i18n/client-imports.test.ts` fails if a client component or anything it
imports reaches the dictionaries.

Text with a variable part keeps `{name}` placeholders in the dictionary and is filled with `interpolate()` from
`src/lib/i18n/interpolate.ts`:

```ts
interpolate(dict.areas.wardMapTitle, { ward: ward.name }) // "Minato, Tokyo map"
```

## Translation Workflow

### Translating New Content

```bash
# Translate all missing content (only creates files that don't exist in ja/)
pnpm translate

# Translate a single file
pnpm translate --file content/blog/new-post.md

# Force re-translate everything
pnpm translate --force

# Preview without writing
pnpm translate --dry-run
```

Requires the `DEEPL_API_KEY` environment variable; the script doesn't read `.env`. Uses the DeepL API with header-based auth.

### After Translation

Translated files are committed to git. They are the source of truth after generation. Human editors can refine translations by editing the Japanese markdown files directly.

## Adding a New Page Route

1. Create the locale-aware implementation under `src/app/[locale]/<page>/page.tsx` (`your-page` below). A page
   whose only param is the locale uses the helpers in `src/app/[locale]/locale-page.ts`:
   ```tsx
   export const dynamicParams = false

   export const generateStaticParams = localeStaticParams

   export const generateMetadata = localizedMetadata('/your-page/', ({ yourPage }) => ({
     title: yourPage.metaTitle,
     description: yourPage.metaDescription
   }))

   export default async function YourPage({ params }: LocalePageProps) {
     const { locale, dict } = localeDictionary(await params)
   ```
2. Add a thin English wrapper under `src/app/(en)/<page>/page.tsx`:
   ```tsx
   import * as localePage from '@/app/[locale]/your-page/page'
   import { englishStaticRoute } from '../route-helpers'

   const route = englishStaticRoute(localePage)

   export const generateMetadata = route.generateMetadata

   export default route.Page
   ```
3. Metadata built from other data uses `localizedPageMetadata({ title, description, path, locale })` from
   `src/lib/seo.ts`, which adds the canonical URL, hreflang alternates, Open Graph and Twitter tags.
4. Make all internal `<Link href>` locale-aware: `localizedRoute("/target/", locale)`.
5. For a route with more dynamic segments, generate only non-default locales and disable dynamic params:
   ```ts
   export const dynamicParams = false

   export async function generateStaticParams() {
     return nonDefaultLocales.flatMap(locale => existingParams.map(p => ({ locale, ...p })))
   }
   ```

## SEO Signals

Every page includes these signals for Google:

| Signal | Implementation |
|---|---|
| `<html lang>` | `"en"` or `"ja"` per locale |
| `hreflang` | Bidirectional `en`, `ja` and `x-default` on a page published in both; a blog post or category published in one language lists only that language and `x-default` |
| Canonical URL | Self-referencing. English: no prefix. Japanese: `/ja/` prefix |
| `og:locale` | `en_US` or `ja_JP` |
| Sitemap | `/sitemap-index.xml` → one child per content group (`src/lib/sitemaps.ts`); each URL lists its published locales as `xhtml:link` hreflang alternates, and both locales of a page sit in the same child sitemap |
| JSON-LD `inLanguage` | Set on WebSite and BlogPosting; never on MedicalBusiness, where schema.org doesn't allow it |
| JSON-LD `knowsLanguage` | MedicalBusiness lists English and Japanese |
| JSON-LD `translationOfWork` / `workTranslation` | BlogPosting schemas link English and Japanese versions as translations, only for a post published in both |
| JSON-LD text and URLs | On `/ja/`, Japanese where the data has it, at the `/ja/` URLs; the business and the site keep one `@id` in both languages ([`seo.md`](agents/seo.md#structured-data)) |

## Pages with English text under `/ja/`

Every page has a `/ja/` route with Japanese page chrome. The legal pages read their Japanese text
from `content/pages/legal/ja/`. The video pages (`/videos/` and `/watch/*`) show a video's
`titleJa` and `descriptionJa` from `src/lib/data/videos.ts` where it has them, and its English
text where it doesn't.

## The 404 page

Cloudflare Pages answers a URL with no file with status 404 and the nearest `404.html`. The export has one,
`out/404.html`: `src/app/global-not-found.tsx` (`experimental.globalNotFound` in `next.config.mjs`) renders it as a
full English document, the site layout around `NotFoundPage` (`src/components/not-found-page.tsx`), with the single
`noindex` robots tag Next.js adds to a 404. Its language switcher goes to `/ja/`. Next.js adds `global-not-found.tsx`
to every route's module graph, so the site fonts it loads through the layout are also preloaded on `/keystatic/`, the
one page without them; a separate `next/font` call in the 404 instead adds its `@font-face` rules to every page's CSS.
Next.js also writes the same page as `out/404/index.html` and `out/_not-found/index.html`; the Pages Function answers
their URLs, and `/404`, with 404 ([`hosts.md`](agents/hosts.md#the-404-pages-own-urls)).

`/ja/...` misses get the same English page. A static export renders not-found UI only as that one root document or as
a `not-found.tsx` boundary, which Next.js serializes into the RSC payload of every page below it, and a Japanese route
rendered and moved after the build would still be a page that the route tests and the SEO audit count.
